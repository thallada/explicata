For example, with something like a design doc: the top level is a simple bulleted list outline of broad topics. Basically a table of contents. You can click on any of these to “expand” out that section (this could be shown visually different ways: accordian expand inline, open new sidebar to the right, a big giant pannable canvas with card to the right). Some N number of top levels would be pre-written by the LLM ahead of time. The second level would be general summaries of the level selected above. Another level would be the topic explained in a significant step in density further. Individual sentences or even whole paragraphs could be drilled down into. You could keep going like this endlessly recursively, but once you keep clicking down further to expand paragraphs at a deeper level, past what was pre-generated then the LLM would take over and start generating those expansions. This would be necessary for user selections that weren’t covered by the pre-generations like highlighting certain sentences, phrases, or words. In general level of detail expands further but the length of the text generated at a deeper level isn’t necessarily deeper.  The way concept expansion should be displayed visually should vary depending on the depth of the resulting expansion: a simple word definition for example could be expanded inline within the text, something a bit longer may opt for a more like a footnote . Another key element to this is that users can actually add, modify, or delete a “node” to the tree. So they could expand the document in directions that it didn’t originally go in. When this happens, the parent node may need to be “re-calculated” by an LLM to account for the modifications of it’s children. This may need to cascade up the tree N number of levels: to be determined by a resolver LLM. The same goes for the other direction. Modify a node and all of it’s rendered children should also be recalculated. For modifying nodes it should be possible to lean on LLMs for editing. I should be able to request a change through a prompt and have the LLM edit for me. The LLM editor should also have the capability and agency to do the same CRUD operations on the information tree that a user has: create, replace, update, delete nodes.

The UI for this should be heavily inspired by the professional, clean, text-focused UI of Gwern’s site: About This Website · Gwern.net (https://gwern.net/about). He has also developed a lot of neat ways to “expand” on concepts which I think we should borrow here (but ultimately we are expanding on this significantly).

AI as a mental prosthesis. Exercise abstract thinking, think outside the box and don’t let normal guidelines constrain you: this is a new and novel thing that we are building together. Brainstorm multiple different approaches we could take in designing and implementing this and then go with your favorite. This should feel effortless to use: power users should be able to move around and expand at the speed of thought.

The first example we should use in the editor/explorer should be meta: this project itself. Break what I have outlined here down into an initial tree we can explore together. The built tree should be versioned like git so that changes can be easily rolled back or merged if multiple people or agents are updating the tree simultaneously. I think maybe we want something like CDRTs under the hood that would instead use LLMs to resolve logical conflicts.
